# Results

## Run 1 — Milestone 3 speedup curve, September 16, 2026

**Workload:** 34 actions — 33 `cc -O2` compiles of generated translation units, plus one link that
depends on all of them. Generated by `testdata/gen_cproject.py --count 32 --iters 400`.

**Host:** Apple M2, 8 logical cores (**4 performance + 4 efficiency**), macOS 26.5.2, Go 1.27.1.

**Host quiet?** *Not certified.* No other builds or benchmarks were started alongside this run, but
background system load was not controlled or measured. Under the protocol this makes the numbers
usable for the shape of the curve and **not** quotable to three significant figures.

**Protocol:** 7 kept runs per configuration, interleaved, first run of each discarded. Every run is
a clean build — there is no cache until Milestone 4.

| Config | Median | IQR | Speedup vs `j=1` |
|---|---|---|---|
| `seq` (reference sequential driver) | 0.913 s | [0.887, 0.988] | 0.98× |
| `j=1` | 0.896 s | [0.879, 0.990] | 1.00× |
| `j=2` | 0.525 s | [0.511, 0.543] | 1.71× |
| `j=4` | 0.310 s | [0.309, 0.316] | 2.89× |
| `j=8` | 0.250 s | [0.246, 0.262] | 3.58× |

### What this shows

**The scheduler costs nothing measurable.** `seq` and `j=1` have overlapping IQRs, and the harness
reported them as inconclusive on its own. The parallel scheduler running one action at a time is
indistinguishable from the sequential reference implementation, which is the result you want: the
goroutine-per-action machinery is not paying for itself out of the build's wall time.

**Speedup is sublinear and flattens: 1.71× at 2 workers, 2.89× at 4, 3.58× at 8.**

The flattening is **not** the graph's shape. This DAG is almost entirely parallel — 33 independent
compiles feeding one link, so the structural critical path is two actions deep out of 34. Nothing
about the dependency structure prevents 8× here.

The most likely explanation is the hardware: the 8 logical cores are 4 performance and 4 efficiency
cores, so the fifth through eighth workers land on substantially slower cores. Going 4 → 8 workers
buys 1.24× rather than 2×, which is the shape that heterogeneity predicts. **This run does not
prove that** — confirming it would need a run pinned to performance cores only, which is not done
here.

### A caveat found while checking, not while planning

The per-run critical path printed by `buildforge build` is **not stable enough to quote as a single
number.** Across four single runs of this same workload it read 551 ms, 136 ms, 145 ms, and 98 ms.

The reason is structural: the measured critical path is a maximum over 33 noisy per-action
durations, and the maximum of many samples is a high-variance statistic. It also inflates under
contention, because an action sharing a core takes longer in wall time than the same action alone.
So the number is a **diagnostic for one run** — it says which chain held that particular build up —
and not a measurement of the graph.

The structural claim survives: the critical path is one compile plus the link, so this workload's
parallelism ceiling is set by the hardware rather than by the DAG. Quoting a specific millisecond
value for it would not.

### Not claimed

- No comparison against Bazel, Buck2, or `make -j` has been run.
- One machine, one workload, one compiler. Nothing here generalizes to other build shapes,
  particularly deep ones where the critical path actually binds.
- The 4 → 8 worker flattening is attributed to core heterogeneity as the most plausible cause,
  and is **not** demonstrated.

## Run 2 — Milestone 4 cache, September 16, 2026

**Workload:** the same 34 actions as Run 1 — 33 `cc -O2` compiles plus one link.
**Host:** Apple M2, 8 logical cores (4 performance + 4 efficiency), macOS 26.5.2, Go 1.27.1.
**Host quiet?** *Not certified*, same as Run 1.
**Protocol:** 7 kept rounds, every configuration run once per round in a fixed order, first round
discarded. Harness: [`cache.py`](cache.py).

| Config | Median | IQR | vs clean | Cached |
|---|---|---|---|---|
| clean (empty cache) | 0.2823 s | [0.2612, 0.3290] | 1.0× | 0/34 |
| no-op rebuild | 0.0098 s | [0.0096, 0.0100] | **28.7×** | 34/34 |
| cosmetic edit (comment) | 0.0374 s | [0.0370, 0.0404] | 7.5× | 33/34 |
| semantic edit (constant) | 0.0753 s | [0.0727, 0.0768] | 3.8× | 32/34 |

No pair of configurations was inconclusive; all four separate cleanly.

### Early cutoff, measured

The two edit configurations differ by one character of intent and by a factor of two in wall time,
and the reason is the row next to them.

A **comment** added to one source file changes that file's digest, so its compile must re-run.
But the object file it produces is byte-identical to the previous one — a comment does not survive
into `.o`. The link's inputs are therefore unchanged, its key is unchanged, and it hits. **33 of 34
cached.**

A **changed constant** re-runs the same compile, but now the object really differs, so the link's
key changes too and it re-runs. **32 of 34 cached.**

This is *early cutoff*: invalidation stops at the point where content stops changing, rather than
cascading to every downstream action. It is not a feature that was implemented — it falls out of
keying on content instead of on timestamps or on "this file was rebuilt". A timestamp-based system
re-links in both cases, because `make` cannot tell that the new `.o` is the old `.o`.

### Deduplication: no benefit on this workload

The CAS holds **34 blobs totalling 60,928 bytes for 34 outputs totalling 60,928 bytes** — exactly
one blob per output, nothing shared.

That is the honest result: every object file in this generated project has different content, so
there is nothing to deduplicate. Splitting the action cache from the CAS is a structural property
that pays off when a workload actually contains repeated bytes — the same header compiled to the
same object by two targets, copied assets, empty files — and this workload contains none. The unit
test `TestBlobsAreDeduplicated` proves the mechanism works; this benchmark shows it buying nothing
here, which is not the same claim.

### Not claimed

- No comparison against Bazel, Buck2, or `make`. The 28.7× no-op figure is BuildForge against
  BuildForge, not against anything else.
- One machine, one workload, one compiler, and a cache small enough to sit entirely in the page
  cache. A cache large enough to miss in RAM would change the no-op number substantially.
- `PATH` is still outside the cache key. Two machines with different compilers on `PATH` could
  share an entry they should not. See the README's "known hole".

## Run 3 — Milestone 5, what hermeticity costs, September 16, 2026

**Workload, host, protocol:** as Run 2. Harness: `cache.py`, once with the sandbox on (the default)
and once with `--no-sandbox`.

| Config | Sandbox on | Sandbox off | Difference |
|---|---|---|---|
| clean | 0.2798 s [0.2531, 0.3120] | 0.2413 s [0.2375, 0.2521] | +16 % |
| no-op | 0.0099 s [0.0098, 0.0099] | 0.0091 s [0.0089, 0.0094] | +9 % |
| cosmetic | 0.0350 s [0.0345, 0.0355] | 0.0339 s [0.0338, 0.0349] | +3 % |
| semantic | 0.0724 s [0.0720, 0.0755] | 0.0667 s [0.0666, 0.0677] | +9 % |

### Why this comparison is weaker than the others, and how much weaker

The two columns come from **two separate benchmark sessions**, not from one interleaved run. The
protocol exists precisely to stop that, so this table is the weakest measurement in this file, and
the no-op row shows by how much.

**A no-op build cannot be affected by the sandbox at all.** A full cache hit returns before any
sandbox directory is created — `tryRestore` runs ahead of `newSandbox` — so the two configurations
execute identical code on that row. They should be the same number. They differ by 9 %, with
non-overlapping IQRs.

That 9 % is therefore not the sandbox. It is session-to-session drift: two invocations minutes
apart on a host whose background load was never controlled. It is also a floor on how much of every
other row is drift rather than signal, which leaves the clean build's +16 % as **something like 5
to 10 % genuinely attributable to hermeticity, and possibly less.**

The honest summary: creating a symlink farm per action and renaming outputs back costs a small
single-digit percentage on this workload, and this experiment cannot pin the number down more
precisely than that. Doing so would need both configurations interleaved inside one session, which
is a change to `cache.py` rather than another run of it.

### Not claimed

- The +16 %, +9 %, +3 % figures are **not** protocol-grade, for the reason above.
- The sandbox is a symlink farm, not a container. It constrains which files inside the workspace an
  action can see; it does not stop an action reading `/usr/include`, its own configuration files, or
  anything else by absolute path. Nor does it stop an action *writing through* a symlink to a
  declared input and modifying the real file.

## Run 4 — Milestone 6 shared cache, September 16, 2026

**Workload, host, protocol:** as Run 2. Harness: [`remote.py`](remote.py), which starts and stops
its own cache server. The remote is populated once before the rounds, so every `remote`
measurement is a hit.

| Config | Median | IQR | vs cold | Cached |
|---|---|---|---|---|
| cold (empty local, no remote) | 0.4023 s | [0.3906, 0.4812] | 1.0× | 0/34 |
| remote (empty local, warm remote) | 0.0241 s | [0.0240, 0.0286] | **16.7×** | **34/34** |
| local (warm local) | 0.0121 s | [0.0117, 0.0126] | 33.2× | 34/34 |

All three configurations separate cleanly; nothing was inconclusive.

**Cross-machine hit rate: 34/34.** A workspace with an empty local cache reproduced the entire
build from work done elsewhere. That only happens because a cache key contains no absolute paths
and no modification times — the decision made in Milestone 4, which had no visible payoff until
this milestone.

**The remote tier costs about 2× the local one** — 24 ms against 12 ms, roughly 0.35 ms per action
to fetch an entry and its blob. The second build on the same machine drops back to the local number
because a remote hit is written into the local store on the way past.

### The number this does not give you

**The server is on localhost.** These measurements exclude everything that makes a real shared
cache hard: round-trip latency, bandwidth limits, TLS, and contention from other clients. On a real
network the remote row would be dominated by per-request latency, and the obvious next step —
batching the entry and blob fetches into one request, which is roughly what Bazel's Remote
Execution API does — would matter enormously and matters not at all here.

So: 16.7× is evidence that the mechanism works end to end, and it is **not** a prediction of what a
shared cache is worth across a building.

### Also verified, not timed

With the server stopped, a build of the same workspace completed normally in 448 ms, produced a
correct binary, and recorded **36 errors** (one failed lookup and one failed upload per action).
A shared cache is an optimization, and an optimization that can break the build is not one.

### Not claimed

- Localhost is not a network, as above.
- Uploads are synchronous, so the cold build that populates the cache pays for them inline. A
  production cache would upload in the background. The cost is in the `cold`-to-warm transition and
  is not separated out here.
- No authentication, no TLS, no eviction. The server is a cache for a trusted network and is not
  claimed to be anything else.

## Run 5 — Milestone 7, and a regression that was not real, September 16, 2026

**Workload, host:** as Run 2.

Adding LRU usage tracking meant `Lookup` writing to each entry file on every hit. Re-running
`cache.py` afterwards showed the no-op build at **0.0120 s [0.0116, 0.0129]**, against **0.0098 s
[0.0098, 0.0099]** recorded in Run 2 — 22 % slower, with IQRs that do not overlap. The mechanism
was obvious: 34 cached actions, one `Chtimes` each.

So the touch was made coarse — skip the write when the entry was already touched within the hour,
paying a `stat` instead. Re-measuring gave **0.0120 s** again. No change at all.

That is the point at which the diagnosis had to be wrong, so the two binaries were compared
properly: one with usage tracking, one with it compiled out, **interleaved inside a single
session**, eleven runs each, first discarded.

| Binary | Median | IQR |
|---|---|---|
| with usage tracking | 13.09 ms | [12.40, 14.35] |
| tracking compiled out | 13.19 ms | [11.80, 15.35] |

**Inconclusive.** The IQRs overlap heavily. The touch costs nothing this workload can measure, and
the 9.8 → 12.0 ms difference was drift between two benchmark sessions run minutes apart — the same
effect Run 3 identified, encountered again from the other direction.

Two things follow. The first is that **Run 2's 0.0098 s and this session's 0.0120 s are not
comparable**, and neither is any other cross-session pair in this file; only the within-session
comparisons carry weight. The second is that the coarse-touch change is kept on its own merits —
not writing to a file on every cache hit is right regardless — and **not** because any measurement
here shows it helps. It was built to fix a regression that turned out not to exist.

### Garbage collection, demonstrated

A cache holding three generations of the same workload, collected from the command line:

```
scanned   38 entries, 38 blobs, 128.71 KB
garbage   0 unreferenced blobs
evicted   29 entries, 29 blobs (budget 40.00 KB)
freed     88.97 KB, now 39.74 KB
```

Then the same build re-run against the collected cache: **34 ok (9 cached)**, correct binary.
Eviction costs time, never correctness — the nine entries that survived still hit, and the rest
re-ran.

"0 unreferenced blobs" is the expected reading for a cache no build was interrupted against. The
unreachable-blob path is covered by `TestGCRemovesUnreferencedBlobs` instead, which stages the
condition directly.

### Not claimed

- No measurement of collection time against a large cache. The collector walks every entry and
  every blob, so it is O(cache size), and nothing here says what that costs at gigabyte scale.
- GC is **not safe to run during a build**. `MinAge` narrows the window in which a blob written
  ahead of its entry looks like garbage; it does not close it. A correct fix needs a lock or a
  two-phase mark, and neither is implemented.
